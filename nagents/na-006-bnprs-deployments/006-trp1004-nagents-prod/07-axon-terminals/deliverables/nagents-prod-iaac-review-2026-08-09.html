1. Merge regression — fixed, please review

Merge 6de1cde (“Merge origin/bp_rel into bp_dev_conflict_fix”) silently truncated nagents-platform/modules/ecs/service/main.tf from 197 lines to 58. These resources were deleted from the module:

aws_ecs_service.this, aws_security_group.task, aws_security_group_rule.from_alb, aws_cloudwatch_log_group.task, aws_appautoscaling_target.ecs, aws_appautoscaling_policy.ecs_cpu, data.aws_region.current, locals

Only aws_ecs_task_definition.this survived. The same merge also declared variable "command" twice. Because outputs.tf still referenced the deleted resources, terraform validate failed with 6 errors on all 9 stacks that use the module — including the live erp-hr-service/prod and projects-backend/prod. No conflict markers were left behind, which is why it passed review.

Nothing could plan, so nothing was destroyed. But there was a real trap: “fixing” this by deleting the dangling references in outputs.tf instead of restoring main.tf would have made the next apply plan a destroy of the live ECS services, log groups, security groups and autoscaling. Please don't take that route if you hit it again.

Fix: restored the whole module directory from origin/nagents_prod. Pardhiv's branch was always clean (197 lines, one command variable), and it is byte-identical per file to 331eccb — the last intact commit, and the version the live prod services were deployed from. So the restore introduces no drift by construction. Commit de4b4aa, now on both bp_rel and bp_dev (bp_dev was an ancestor, so a fast-forward resynced them). All 9 stacks validate again.

Two asks: someone with the service terraform.tfvars should run a confirming plan on erp-hr-service/prod and projects-backend/prod — I could not, as those files hold secrets I don't have. And going forward, please terraform validate every consumer of a shared module after a conflict resolution, not just the stack being worked on. That is the only reason this surfaced.

2. Route 53 — agreed

Keeping the record commented out until the FQDN is confirmed is the right call, and the guard comment about never uncommenting with an empty name is a good catch. One constraint for when you choose it: the ALB cert is *.prod.itpgateway.com, which covers exactly one label. So accounts.prod.itpgateway.com works; anything deeper such as kc.accounts.prod.itpgateway.com needs a new certificate. KC_HOSTNAME, host_header_values and the A record must all be that same name.

3. Keycloak — changes before apply

The stack validates cleanly and every platform remote-state output it consumes exists. Listener priority 500 is free on both :80 and :443, the to_rds SG rule won't clobber the platform's rules, and dropping the tracked terraform.tfvars was the right move. Five things I'd change first:

# Issue
1 Apply will fail as-is. host_header_values defaults to [], so the dynamic "condition" emits nothing — and an ALB listener rule must have at least one condition. Set it together with keycloak_hostname.
2 Don't run Keycloak as the RDS master user. db_username defaults to nagents_admin, the Postgres superuser, and its password is copied into a second secret. Rotating the master password will silently break Keycloak — which is exactly what already happened on utms (utms/prod/keycloak holds an invalid bootstrap password today). Please create a dedicated keycloak role owning only the keycloak schema.
3 Deprecated bootstrap vars. KEYCLOAK_ADMIN / KEYCLOAK_ADMIN_PASSWORD were renamed to KC_BOOTSTRAP_ADMIN_USERNAME / KC_BOOTSTRAP_ADMIN_PASSWORD in Keycloak 26. They still work on 26.4.7 but warn, and only take effect on first boot against an empty database.
4 First boot will likely crash-loop. command = ["start"] without --optimized re-runs Quarkus augmentation on every task start, and the ecs/service module has no health_check_grace_period_seconds. The target group kills a task after 3 × 30s = 90s. Add a grace period (~300s) to the module, or ship a prebuilt image with --optimized. This looks like what drove 5b39824.
5 KC_FEATURES = "scripts" is a preview feature enabling server-side JavaScript in protocol mappers — meaningful attack surface on an IdP. If it's utms parity rather than a real requirement, please drop it.

Minor: add lifecycle { ignore_changes = [secret_string] } to aws_secretsmanager_secret_version so a console-rotated admin password isn't reverted, and consider recovery_window_in_days = 0 so a destroy/recreate doesn't collide on the secret name.

One observation rather than a Keycloak defect: the :80 rule forwards instead of redirecting, so Keycloak would serve login and the admin console over plaintext HTTP. The existing erp-api and projects-api rules do the same, so it's a platform-wide convention — but it matters considerably more for an IdP than for an API. Worth fixing across the board.

4. On the “new Keycloak URL”

To set expectations: prod Keycloak is not deployed, so there is no URL yet. I checked every surface in ap-south-2 — no Terraform state under services/keycloak/prod/, no ECS service, no target group, no listener rule, no task definition, no secret, and none of accounts/keycloak/auth.prod.itpgateway.com resolve.

Prod authenticates today against the shared IdP:
https://accounts-uat.itpgateway.com/realms/BNPRS-enterprise

That is live and working — I ran a real PKCE authorization request and both hr-spa and projects-frontend get the login form, so the old prod redirect-URI blocker is resolved. Note the misleading -uat in a hostname that serves prod; that's very likely where the “newly deployed Keycloak” expectation came from.

Separately, one security item for the shared-Keycloak owners: a control request with a deliberately unregistered redirect_uri also returned the login form for hr-spa. That means the client has a wildcard valid-redirect-URI on the shared realm — an open redirector, where an attacker can send a victim through a genuine accounts-uat.itpgateway.com login and have the authorization code delivered to a host they control. It should be tightened to explicit URIs.
